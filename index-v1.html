how lilithlist works

A product model for peer warning with minimization, correction, and due-process safeguards built in.

CONTENTSthreat modelposting rulesnetwork modelcorrection + removalurgent situations

Threat model

LilithList is designed around a simple premise: the board should not become a second source of danger. The useful unit is a conduct warning linked to a partial identifier—not a public dossier on a person.

  • No legal names, faces, exact addresses, full phone numbers, IDs, or precise live locations.
  • Reports expire by default and must be renewed through corroboration.
  • Search is exact-fragment oriented; bulk browsing and indexing are discouraged.
  • Workers choose what local node to trust. No global identity graph is required.

Posting rules

  1. Share only what another worker needs to make a screening or safety decision.
  2. Separate observed behavior from inference. Use dates broadly.
  3. Never identify another worker without clear, revocable consent.
  4. High-risk flags need peer review; positive notes cannot erase warnings.
  5. False, retaliatory, discriminatory, or promotional posts are removed.

Network model (concept)

worker device → encrypted draft → trusted local node
trusted node → moderation receipt → signed, minimized bulletin
signed bulletin ↔ selected peer mirrors

NO central profile · NO ad network · NO public API · NO bulk export

The interface here is a front-end concept. A real deployment would need end-to-end encryption, device security review, legal analysis by jurisdiction, abuse-resistant moderation, independent security testing, and a carefully governed federation protocol.

Correction + removal

Every bulletin should carry a stable receipt. A reporter can correct or revoke it. A subject can contest inaccurate information through a privacy-preserving channel. Nodes show dispute state and moderation history without exposing the parties. Emergency unpublishing propagates before the appeal is resolved.

Urgent situations

This board is not emergency dispatch. If someone is in immediate danger, use the safest trusted local resource available to them. Product copy should never assume police contact is safe, wanted, or available. A production build should let each community node maintain its own verified crisis and mutual-aid directory.
